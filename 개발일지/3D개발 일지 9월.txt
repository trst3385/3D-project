게임 시작 전 카운트다운 중 ESC 일시정지 예외 처리 및 UI/UX 개선

- 게임 시작 전 3초간의 카운트다운(준비 상태) 중에  ESC 키를 누르면 뜨는 일시정지 창이 활성화 되어도 게임 속도가 정상적으로 흘러버리는 연출/시간 동기화 꼬임 현상 발생.
- 원인: 준비 상태에 대한 명확한 예외 처리가 없었고, PauseManager 스크립트가 Time.timeScale을 무조건 반전시키는 로직만 가지고 있었기 때문.

- 해결 및 구현 과정.
   1. 상태 관리 도입 (GameManager): IsGameReady 플래그 변수를 추가해서 현재 카운트다운(준비) 진행 중인지 여부를 외부에 안전하게 노출(private set)
   2. 입력 예외 처리 (PauseManager): ESC 입력 시 작동하는 PauseManager의 TogglePause() 함수에 GameManager.Instance.IsGameReady 검증 로직을 추가해, 카운드다운 중일 때는 일시정지 창이 아예 켜지지 않도록 차단
   3. UX 개선 및 안내 텍스트 도입 (UIManager):
      3-1. 이렇게 변경을 했지만 사용자는 영문도 모른 채 카운트다운 중에 ESC가 안 먹힌다고 오해하지 않도록,
      화면에 PauseWarningText UI를 띄워 "카운트다운 중에는 일시정지할 수 없습니다"라는 안내 메시지를 1.5초간 노출하는 코루틴 로직을 구현 (WaitForSecondsRealtime 활용하여 정지 중에도 작동 보장)
      3-2. UIManager 스크립트도 싱글톤 패턴을 적용하여 전역 접근성을 확보

- 아키텍처 및 설계 고민.
   1. 관심사 분리 (Separation of Concerns / SRP):
      1-1. 수정 초기에는 PauseManager 스크립트가 직접 텍스트 문구를 들고 있게 하려고 했지만, UI 문구 관리 책임은 화면의 UI를 담당하는 UIManager 스크립트가 담당해야 한다는 점을 깨닫고 구조를 다시 리팩토링했어
      1-2. PauseManager 스크립트는 구체적인 문자열을 알 필요 없이 오직 "경고를 띄워라"라는 명령(메서드 호출)만 UIManager 스크립트에 던지도록 결합도를 낮추고 응집도를 높임
         1-a. 하지만 지금 방식은 각 매니저들끼리 싱글톤으로 부르기에 완전한 느슨한 결합 상태는 아니야. 하지만 꼭 *강한결합은 안된다* 라는 강박이 들면 안돼. 지금 내 상황에선 어떤게 최선이고, 이 방식의 장단점을 알고 내가 왜 결국 이 방식을 채택 했는지 대답 할 줄 알아야해
   2. 오늘은 그저 단순히 버그를 고치는것에 급급하지 않고, "이 코드가 이 클래스에 있는 게 맞는건가?", "싱글톤과 결합도를 어떻게 타협해야 할까?" "SRP를 너무 지켜서도 안되고, 그렇다고 무시해서는 안돼",
      등 객체지향적 관점과 아키텍처의 한계를 깊이 고민해 볼 수 있었던 짧지만 내가 그만큼 성장 했다는 의미 있는 시간이었어
   3. 주말엔 쉬기로 한 약속을 어겼지만 오늘은 예외로 치자. 찜찜했던 문제를 해결했고 내가 코드의 아키텍처를 많이 고민했고 어떤 방식으로 해결 했는지 주도적으로 판단한 날이었으니까!

UIManager스크립트 내 이벤트 구독 해제 및 메모리 누수 방지 리팩토링

- v0.4.1 빌드 이후, UIManager 스크립트에서 이벤트 구독 패턴에서 발생할 수 있는 잠재적 버그(메모리 누수 및 댕글링 참조) 점검 및 아키텍처 안정성 확보.

- 이벤트 구독 해제(OnDestroy) 보완.
   1. UIManager가 파괴될 때 GameManager와 PlacementManager 스크립트에서 구독 중이던 모든 이벤트(OnEnemyCountChanged, OnRoundChanged, OnGoldShortage)에 대해 -= 연산자로 구독 해제 로직을 누락 없이 짝을 맞춰 구현
   2. 익명 람다식의 한계 극복 (메모리 누수 방지):
      2-1. 기존에 라운드 변경 이벤트(OnRoundChanged)를 처리할 때 사용했던 익명 람다식((newData) => ...)은 등록할 때와 해제할 때의 메모리 주소가 달라져 정상적인 구독 해제가 불가능하다는 점을 학습
      2-2. 이를 해결하기 위해 명시적인 일반 함수 HandleRoundChanged() 로 분리해서 정확한 참조 해제가 가능하도록 구조를 개선
   3. 데이터 형식 매칭 (중간 다리 역할 정립): OnRoundChanged가 던져주는 RoundData(ScriptableObject) 에셋 덩어리에서 필요한 enemyCount(목표 처치 수) 데이터를 추출해서, 기존 UI 갱신 함수(UpdateUI)와 자연스럽게 연동되도록 중간 다리 역할을 성공적으로 정립

- OnDestroy()에서의 OnRoundChanged -= HandleRoundChanged와 HandleRoundChanged() 함수의 이해
   1. 문제 상황 (람다식의 함정):
      1-1. 처음에는 라운드 변경 이벤트(OnRoundChanged)를 처리할 때 람다식((newData) => { ... })을 사용
      1-2. 하지만 람다식은 이름이 없는 일회용 함수라서, 등록할 때(+=)와 해제할 때(-=) 컴퓨터가 인식하는 메모리 주소가 달라져
      1-3. 이 때문에 나중에 UIManager가 파괴되어도 이벤트 구독이 해제되지 않아 메모리 누수(Memory Leak)를 일으키는 치명적인 버그가 발생
   2. 해결 방법 (일반 메서드로 분리):
      2-1. 람다식을 버리고, 고유한 이름표를 가진 일반 메서드HandleRoundChanged()를 새로 만듦.
      2-2. 등록할 때(+= HandleRoundChanged)도, 해제할 때(-= HandleRoundChanged)도 똑같은 이름표(주소)를 가리키게 되므로 컴퓨터가 헷갈리지 않고 정확하게 구독을 끊어낼(메모리 해제) 수 있게 되지
   3. 데이터 형식을 맞춰주는 '중간 다리' 역할:
      3-1. OnRoundChanged 이벤트는 RoundData(ScriptableObject 에셋 덩어리)를 통째로 던져주는데, 기존 UI 갱신 함수인 UpdateUI(int current, int total)과는 데이터 형태(시그니처)가 맞지 않아
      3-2. 그래서 HandleRoundChanged(RoundData newData) 함수가 중간에서 신호를 받아, 그 신호 안에 있는 newData.enemyCount(목표 처치 수)만 쏙 빼서 UpdateUI()한테 전달해 주는 중간 다리 역할을  수행


**UiManager에서의 골드 부족시 뜰 텍스트, 카운드다운 중 일시정치 창 등장 불가 텍스트를 하나의 코루틴으로 관리. 텍스트 내용을 하드코딩으로 스크립트 안에 적을지, 매개변수나 인스펙터로 빼서 이곳에 적을지 고민 해보자**
