   이로 인해 오히려 의존성이 복잡해지고 관리 비용이 증가하는 비효율이 생각났어

   2. AudioSource 컴포넌트의 Output을 유니티 AudioMixer의 BGM 그룹에 직접 라우팅하여, 추후 환경설정(Settings) 구현 시 마스터 채널을 통한 일괄 볼륨 제어가 가능하도록 아키텍처적 유연성 확보,
   (2D작품처럼 사운드, 효과음 둘만 만들 수도 있어. 아니면 이 셋 전부 넣는것도 고려해야지)

- 기술적 고민 및 해결 (Troubleshooting).
   1. 오랫만에 사운드 시스템을 추가하느라 시간이 많이 지채됐어
   2. 현상: 오디오 시스템을 오랜만에 재구축하는 과정에서 발생한 시행착오로, 스크립트 하나만으로 오디오 소스를 제어하려 할 때 Play On Awake를 끄면 씬 진입 시 배경음악이 무음으로 처리되는 문제 직면
   3. 원인 분석: 명시적인 재생 함수(PlayBGM) 호출 타이밍이나 초기화 로직이 연결되지 않은 상태에서 컴포넌트 자동 생성 방식(AddComponent)에만 의존하려다 발생한 세팅 누락
   4. 해결 및 정립: 불필요한 코드 주도형 동적 로딩을 과감히 걷어내고, 유니티 에디터의 직관적인 컴포넌트 구조(AudioSource + AudioMixer)를 적극 활용,
   매니저 스크립트는 하드코딩된 파일 로드가 아닌 전역 제어와 씬 유지(State Management)라는 본연의 역할에 집중하도록 구조 재정립

   1. 노션 문서화에서 실체적 코드로의 전환: 지난 한 달간 노션 기록을 통해 시스템의 논리와 설계 구조를 문서화하는 데 집중했다면,

      1-1. 이 사운드 시스템을 만들면 노션에도 새로운 트러블슈팅 기록을 적을 수도 있지, 지금 노션의 기록은 솔직히 이미 있던 문제들을 뒤져서 찾아낸거라 내용이한정적, 비슷할 내용일 수 밖에 없어

ESC 옵션창에 BGM 볼륨 조절 구현
GameObject.Find vs Resources.Load의 차이

- SoundManager 아키텍처 구축.
   1. 싱글톤 및 DontDestroyOnLoad 적용으로 씬 전환 시에도 사운드 상태 유지
   2. 오디오 믹서(AudioMixer) 볼륨 제어 로직 구현 (Mathf.Log10을 활용한 선형 슬라이더 값을 데시벨(-80dB ~ 0dB)로 변환)
   3. 오디오 믹서는 Resources.Load로 찾으면 메모리에 부담이 크기에 이 부분만은 직업 인스펙터에 드래그&드롭 방식으로 연결했어, 만일 인스펙터 연결 누락 시 휴먼 에러를 방지하기 위한 Debug.LogError 방어 코드 추가

- PauseManager UI 자동 탐색 및 연동.
   1. 기존의 UI 찾기인 씬 내 비활성화(SetActive(false)) 상태로 존재하는 PausePanel을 Resources.FindObjectsOfTypeAll<Canvas>()와 프리팹 필터링을 통해 안전하게 탐색 후 비활성화 유지
   2. PausePanel패널 패널 내부 자식 컴포넌트인 BGM 슬라이더 (BGM_Slider)를 GetComponentInChildren<Slider>(true)로 안정적으로 찾기
   3. if (bgmSlider != null) 조건문 안에 bgmSlider.onValueChanged.AddListener() 코드를 이용해 슬라이더 이벤트 발생 시 SoundManager의 볼륨 조절 함수가 자동으로 호출되도록 리스너를 동적으로 등록하고, 시작 기본값(0.75f)을 세팅

- UI 시인성 개선: ESC 옵션창 내 슬라이더 상단에 TMP(TextMeshPro) 레이블("BGM")을 추가하여 유저 직관성 향상.


- GameObject.Find vs Resources.Load의 차이?
   1. GameObject.Find (씬 탐색):
      1-1. 대상: 이미 현재 씬(Scene)에 배치되어 메모리에 떠 있는 게임 오브젝트
      1-2. 특징: Hierarchy 창에 활성화(Active)된 오브젝트만 이름으로 찾아옴. (비활성화된 객체는 못 찾음)
      1-3. 내가 주로 UI나 Hierarchy 창에 있는 각종 매니저 오브젝트를 찾을때 쓰고있어
   2. Resources.Load (프로젝트 에셋 로딩):
      2-1. 대상: 아직 씬에 없고 프로젝트 폴더(Assets/Resources/)에 저장되어 있는 에셋 파일(프리팹, 오디오 믹서, 텍스처 등)
      2-2. 특징: 프로젝트 폴더의 파일을 코드로 직접 읽어와 런타임 메모리에 새로 올림. (메모리 파편화 및 관리 부담으로 실무에선 지양!!)
      2-3. 폴더에 있는 메인화면씬, 게임씬만 찾을때만 극히 드물게 써 (일일히 수동 연결을 지양하는 편이라서)
   3. Resources.FindObjectsOfTypeAll<T>()는 뭐야?
      3-1. 이름의 오해: 이름에 Resources가 붙어있지만, 프로젝트 폴더(Resources 폴더)를 뒤지는 기능이 아냐
      3-2. 실제 역할: 현재 유니티 메모리(RAM)상에 로드되어 있는 모든 오브젝트를 검색하는 C# API 클래스 함수
      3-3. 사용 목적: GameObject.Find와 달리 씬 내에 비활성화(SetActive(false))되어 숨어있는 오브젝트까지 포함해서 전수조사할 수 있어 (비활성화 상태로 실행하는 옵션창(PausePanel패널 등에 쓰고 있어)
         ex) Resources.FindObjectsOfTypeAll<Canvas>()로 씬의 모든 캔버스를 가져온 뒤, 그 자식인 비활성화된 PausePanel을 찾아내는 용도로 활용

- 느낀 점 & 배운 점.
   1. 인스펙터 수동 연결의 단점(휴먼 에러)을 방어 코드(Debug.LogError)로 보완하고, 씬 내 비활성화된 UI 객체는 코드로 유연하게 찾아내는 역할 분담 방식을 정립 (Find, Resources.Load
   2. 불필요한 과도한 엔지니어링(옵저버 패턴 등)을 배제하고, 일대일로 명확히 종속되는 구조에서는 싱글톤 직접 호출이 가독성과 유지보수 면에서 더 효율적임을 확인
      2-1. 물론 그에따른 단점(메모리 부하에 대한 경각심은 항상 가지고 있어야 하고, 그에 따른 대처법이나 다른 방법도 알아야 하는것도 중요하지. 지금 내 프로젝트는 소규모라 써도 큰 부하는 없지만 실무에서의 규모는 크니까 그 위험성을 잘 알아둬야해)

**옵저버 패턴을 사용한 이유에 대해 따로 문제 해결 란에 적기**
**자료구조, 알고리즘, 데이터베이스, 네트워크, 운영체제, 그래픽스는 틈틈히 공부**
**UI나 오브젝트 등 이름으로 찾기하면 이름 변경 등 변경되면 큰 오류 발생 가능성, 이에 태그Tag로 찾는 방식도 고려 할 수 있다를 어필**
**포폴이나 git에 핵심적인 내용을 더욱 부각 시킬 필요가 있어** **다만 포트폴리오를 보는 사람의 입장에서 가장 먼저 눈에 띄고 감탄할 만한 핵심 기술 트러블슈팅(예: 오늘 쓴 SRP 구조 개선 같은 내용)을 상단에 배치하고**
   1. 그러니까 무슨 고민을 했는지 어떻게 혹은 왜 밑바닥을 기어 다녔는지를 보여줘야지. 그게 너의 깊이인건데. 
      그리고 그런 애들을 전면에 내세워서 강조해야지 나머진 전부 곁가지임. 그냥 딱 노션만 열어도 그것부터 보이게끔 해봐. 그리고 포폴은 얼만큼의 노력이 아니라 어떤 깊이의 노력인지를 보여주는 공간이어야 된다고 생각함
   2. 뽑는 입장에서 너무 기초적인 부분이 구현의 성과로 어필되면 긍정적으로 보이기 어려울 것 같다고 생각해. 분량이 좀 덜어져야 페이지도 보기 좋게 정리가 될 것 같아. 지금 2열로 배치된게 읽기가 좀 힘든데 분량이 줄어들면 그냥 1열로 세로로 길게 쓸 수 있을 것 같거든
   3. 노력이 시간낭비는 아니지. 남의 말을 듣고 받아들여서 네 노력을 보여주라는거임. 열심히 한건 알겠는데 수준이 너무 떨어져. 튜토리얼 수준의 개념들을 그저 뭘 깨달았다만 알려주는 수준이잖아. 저건 너 아니고 다른 사람들도 다 똑같이 경험하는거야,
   그걸 토대로 뭘 더 심화해서 발전시켰는지를 보여주는게 중요한거고. 그리고 윗댓처럼 저런 내용들만 보이면 진짜 네 노력이 거기 묻혀서 안보이는거임
   4. 노션 포폴 페이지 보니까 핵심만 남겨도 될 것 같다고 느꼈어. 예를 들어서 게임의 전반적인 플레이 규칙을 다 소개하고 있는데 이건 사실 통째로 날려도 플머 포폴로서는 큰 문제가 안될 것 같아,
      나도 졸업작품으로 만든 게임 포폴에 냈는데, 어떤 게임인지는 장르만 한 줄로 설명하고 바로 기술적인 문제 해결한 사례들 나열했거든. 그리고 문제해결이나 구현 과정에 대한 것도 어필할 부분 몇 가지만 골라내는게 좋을 것 같아. 같이 힘내보자 화이팅

   2-1인스펙터 드래그: "직관적이고 빠르게 값을 바꿀 수 있어서 썼습니다." (정답)
   2-2.싱글톤: "게임 전역에서 하나만 존재해야 하는 관리자(GameManager 등)가 필요해서 썼습니다." (정답)
   2-3. 옵저버 패턴: "UI와 로직을 분리하여 의존성을 줄이고 싶어서 썼습니다." (정답)
   2-4.포트폴리오에는 1~2개의 패턴만 확실하게 보여줘도 충분해. 오늘 내가 한 것처럼 데이터(SO)를 잘 활용하고, 의존성 주입(DI)을 이해하고 있다는 것만 보여줘도 신입 수준에선 베스트일거야!
3. 왜? 이런 방식의 작품을 만들었냐, 무슨 생각을 하면서 만들었냐를 적어보자
   3-1. 데이터의 외부화: 지금처럼 ScriptableObject로 데이터(수치)를 완벽하게 분리하고, "기획자가 엑셀로 데이터를 관리한다고 가정했을 때, 이를 어떻게 유니티에 불러올까?"를 고민해 봐
   3-2. 생명주기 관리 (Object Pooling): Instantiate와 Destroy를 계속 쓰면 메모리가 파편화돼. 총알을 100개 미리 만들어두고 껐다 켰다 하는 '오브젝트 풀링(Object Pooling)'을 적용해 봐. 이건 게임 개발자라면 반드시 물어보는 필수 질문이야!
   3-3. 예외 처리와 로깅: Try-Catch를 쓰거나, 데이터가 없을 때 Debug.LogError로 멈추는(Fail-fast) 로직. "예상치 못한 상황이 벌어졌을 때 프로그램이 죽지 않고 어떻게 로그를 남길 것인가"에 대한 고민
4. '왜' 결합도를 낮추려고 했는지 적어두기: "결합도를 낮추니 깔끔해졌다"는 결과도 좋지만, "결합도가 높으면 A 코드를 수정할 때 B 코드까지 건드려야 해서 수정이 번거롭고 복잡했는데 옵저버 패턴 등 이벤트 신호를 전하고 받는 식으로 수정하니,
   이젠 걱정이 사라졌다" 같은 감정을 한 줄 덧붙이면, 현업 개발자의 고충을 이미 경험하고 해결했다는 게 더 잘 느껴질거야!
