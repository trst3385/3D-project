게임 시작 전 카운트다운 중 ESC 일시정지 예외 처리 및 UI/UX 개선

- 게임 시작 전 3초간의 카운트다운(준비 상태) 중에  ESC 키를 누르면 뜨는 일시정지 창이 활성화 되어도 게임 속도가 정상적으로 흘러버리는 연출/시간 동기화 꼬임 현상 발생.
- 원인: 준비 상태에 대한 명확한 예외 처리가 없었고, PauseManager 스크립트가 Time.timeScale을 무조건 반전시키는 로직만 가지고 있었기 때문.

- 해결 및 구현 과정.
   1. 상태 관리 도입 (GameManager): IsGameReady 플래그 변수를 추가해서 현재 카운트다운(준비) 진행 중인지 여부를 외부에 안전하게 노출(private set)
   2. 입력 예외 처리 (PauseManager): ESC 입력 시 작동하는 PauseManager의 TogglePause() 함수에 GameManager.Instance.IsGameReady 검증 로직을 추가해, 카운드다운 중일 때는 일시정지 창이 아예 켜지지 않도록 차단
   3. UX 개선 및 안내 텍스트 도입 (UIManager):
      3-1. 이렇게 변경을 했지만 사용자는 영문도 모른 채 카운트다운 중에 ESC가 안 먹힌다고 오해하지 않도록,
      화면에 PauseWarningText UI를 띄워 "카운트다운 중에는 일시정지할 수 없습니다"라는 안내 메시지를 1.5초간 노출하는 코루틴 로직을 구현 (WaitForSecondsRealtime 활용하여 정지 중에도 작동 보장)
      3-2. UIManager 스크립트도 싱글톤 패턴을 적용하여 전역 접근성을 확보

- 아키텍처 및 설계 고민.
   1. 관심사 분리 (Separation of Concerns / SRP):
      1-1. 수정 초기에는 PauseManager 스크립트가 직접 텍스트 문구를 들고 있게 하려고 했지만, UI 문구 관리 책임은 화면의 UI를 담당하는 UIManager 스크립트가 담당해야 한다는 점을 깨닫고 구조를 다시 리팩토링했어
      1-2. PauseManager 스크립트는 구체적인 문자열을 알 필요 없이 오직 "경고를 띄워라"라는 명령(메서드 호출)만 UIManager 스크립트에 던지도록 결합도를 낮추고 응집도를 높임
         1-a. 하지만 지금 방식은 각 매니저들끼리 싱글톤으로 부르기에 완전한 느슨한 결합 상태는 아니야. 하지만 꼭 *강한결합은 안된다* 라는 강박이 들면 안돼. 지금 내 상황에선 어떤게 최선이고, 이 방식의 장단점을 알고 내가 왜 결국 이 방식을 채택 했는지 대답 할 줄 알아야해
   2. 오늘은 그저 단순히 버그를 고치는것에 급급하지 않고, "이 코드가 이 클래스에 있는 게 맞는건가?", "싱글톤과 결합도를 어떻게 타협해야 할까?" "SRP를 너무 지켜서도 안되고, 그렇다고 무시해서는 안돼",
      등 객체지향적 관점과 아키텍처의 한계를 깊이 고민해 볼 수 있었던 짧지만 내가 그만큼 성장 했다는 의미 있는 시간이었어
   3. 주말엔 쉬기로 한 약속을 어겼지만 오늘은 예외로 치자. 찜찜했던 문제를 해결했고 내가 코드의 아키텍처를 많이 고민했고 어떤 방식으로 해결 했는지 주도적으로 판단한 날이었으니까!

UIManager스크립트 내 이벤트 구독 해제 및 메모리 누수 방지 리팩토링

- v0.4.1 빌드 이후, UIManager 스크립트에서 이벤트 구독 패턴에서 발생할 수 있는 잠재적 버그(메모리 누수 및 댕글링 참조) 점검 및 아키텍처 안정성 확보.

- 이벤트 구독 해제(OnDestroy) 보완.
   1. UIManager가 파괴될 때 GameManager와 PlacementManager 스크립트에서 구독 중이던 모든 이벤트(OnEnemyCountChanged, OnRoundChanged, OnGoldShortage)에 대해 -= 연산자로 구독 해제 로직을 누락 없이 짝을 맞춰 구현
   2. 익명 람다식의 한계 극복 (메모리 누수 방지):
      2-1. 기존에 라운드 변경 이벤트(OnRoundChanged)를 처리할 때 사용했던 익명 람다식((newData) => ...)은 등록할 때와 해제할 때의 메모리 주소가 달라져 정상적인 구독 해제가 불가능하다는 점을 학습
         2-a "아, 데이터 형식이 달라서 중간에 이걸 맞게 변환할게 필요하구나!"
      2-2. 이를 해결하기 위해 명시적인 일반 함수 HandleRoundChanged() 로 분리해서 정확한 참조 해제가 가능하도록 구조를 개선
   3. 데이터 형식 매칭 (중간 다리 역할 정립): OnRoundChanged가 던져주는 RoundData(ScriptableObject) 에셋 덩어리에서 필요한 enemyCount(목표 처치 수) 데이터를 추출해서, 기존 UI 갱신 함수(UpdateUI)와 자연스럽게 연동되도록 중간 다리 역할을 성공적으로 정립

- OnDestroy()에서의 OnRoundChanged -= HandleRoundChanged와 HandleRoundChanged() 함수의 이해
   1. 문제 상황 (람다식의 함정):
      1-1. 처음에는 라운드 변경 이벤트(OnRoundChanged)를 처리할 때 람다식((newData) => { ... })을 사용
      1-2. 하지만 람다식은 이름이 없는 일회용 함수라서, 등록할 때(+=)와 해제할 때(-=) 컴퓨터가 인식하는 메모리 주소가 달라져
      1-3. 이 때문에 나중에 UIManager 스크립트가 파괴되어도 이벤트 구독이 해제되지 않아 메모리 누수(Memory Leak)를 일으키는 치명적인 버그가 발생
   2. 해결 방법 (일반 메서드로 분리):
      2-1. 람다식을 버리고, 고유한 이름표를 가진 일반 메서드HandleRoundChanged()를 새로 만듦.
      2-2. 등록할 때(+= HandleRoundChanged)도, 해제할 때(-= HandleRoundChanged)도 똑같은 이름표(주소)를 가리키게 되므로 컴퓨터가 헷갈리지 않고 정확하게 구독을 끊어낼(메모리 해제) 수 있게 되지
   3. 데이터 형식을 맞춰주는 '중간 다리' 역할:
      3-1. OnRoundChanged 이벤트는 RoundData(ScriptableObject 에셋 덩어리)를 통째로 던져주는데, 기존 UI 갱신 함수인 UpdateUI(int current, int total)과는 데이터 형태(시그니처)가 맞지 않아
      3-2. 그래서 HandleRoundChanged(RoundData newData) 함수가 중간에서 신호를 받아, 그 신호 안에 있는 newData.enemyCount(목표 처치 수)만 쏙 빼서 UpdateUI()한테 전달해 주는 중간 다리 역할을  수행


**오브젝트 풀링(Object Pooling)에 대해서도 뭘 해보거나 만들어보자, 이론만 알지 이걸 실제로 경험하지 못해서 아예 모르는거랑 다름 없는 상태랑 똑같은것 같아**

내일 AI면접 대비 예상 문제를 빠르게 이해

- Array(배열): 처음 만들 때 방의 개수(크기)를 정해두면, 절대 늘리거나 줄일 수 없어. 예를 들어 new GameObject[10] 하면 무조건 10개짜리 방만 생기는 거야.
   1. 특징: 내부 메모리 위치가 연속적으로 딱 정해져 있어. new gameObject[4]처럼 처음에 4개로 선언하면 끝이야. 인덱스(방 번호)를 알면 데이터 접근이 엄청나게 빠르지만(O(1)), 
   공간을 늘리거나 줄일 수 없어서 추가적인 아이템을 담으려면 새로 배열을 만들거나 코드를 고쳐야 하므로 유지보수성이 낮아.
   2. 게임에서 언제 써?: 게임 중 절대로 방 개수가 변하지 않는 고정된 데이터. (예: 1년 12달 데이터, 캐릭터의 고정된 스탯 항목들)
- List: Array의 단점을 보완한 버전. 방 개수를 미리 안 정해도 되고, 데이터가 들어올 때마다 알아서 공간을 늘리거나 줄여줘(Add(), Remove()). 유니티에서 가장 흔하게 쓰는 자료구조
   1. 특징: 내부적으로는 배열을 쓰지만, 방이 꽉 차면 List가 알아서 더 큰 배열을 새로 만들고 기존 데이터를 이사시키는 방식(Count와 Capacity)으로 작동해. 덕분에 데이터를 자유롭게 추가(Add)하고 삭제(Remove)할 수 있어 유지보수성이 아주 좋아
   2. 언제 써?: 이번 라운드에 살아있는 적들(List<Enemy>), 플레이어가 먹은 아이템 목록 등 개수가 계속 변하는 것들 (내 GameManager의 현재 살아있는 적 리스트처럼)
   3. 주의할 점!: 리스트 중간에 있는 데이터를 삭제하면, 뒤에 있는 데이터들이 빈자리를 채우려고 앞으로 한 칸씩 다 이사를 가야 해서 CPU 과부하가 걸려. 
   그리고 방이 꽉 차서 이사할 때(Resize)도 연산 비용이 드니까, 대략적인 크기를 안다면 처음에 new List<int>(50)처럼 예측 크기를 지정해 주는 게 최적화에 좋아
- Dictionary (딕셔너리): 데이터를 넣을 때 Key(이름표)와 Value(알맹이) 쌍으로 저장하는 구조.
   1. 장점: 리스트처럼 처음부터 끝까지 다 뒤질 필요 없이, 이름표(Key)만 딱 던지면 그 데이터가 어디 있는지 단 1초 만에(해시 알고리즘으로) 찾아냄. 검색 속도가 빠름
   2. 단점: 순서가 뒤죽박죽일 수 있고, 키가 겹치면 에러가 나기 때문에 관리할 때 조금 더 신경 써야 해
   3. 언제 써?: 아이템 ID로 아이템 정보를 바로 찾을 때, 플레이어 업적이나 스킬 데이터베이스를 관리할 때
- "데이터를 순차적으로 탐색해야 할 때는 리스트를 쓰지만, 아이템 ID나 몬스터 종류처럼 고유한 Key 값을 이용해 데이터를 지연 없이 즉시 찾아야 할 때는 Dictionary와 ScriptableObject를 결합하여 데이터베이스 형태로 관리하는 구조를 선호합니다."


- Queue: (First In, First Out 선입선출): 먼저 들어온 데이터가 먼저 처리돼서 빠져나가는 구조야. 가게 앞에 줄 서는 거나 은행 번호표 뽑는 걸 생각하면 돼
   1. 게임에 어디에 써?
      1-1. 몬스터 스폰 대기열: 몬스터가 순서대로 스폰되어야 할 때 줄을 세워두고 차례대로 내보낼 때
      1-2. 턴제 게임 행동 예약: 플레이어가 명령한 행동들을 순서대로 밀어 넣고 차례차례 실행할 때(커맨드 큐)
   2. 핵심 키워드: 선입선출, 줄 서기
- Stack: (Last In, First Out 후입선출): 가장 마지막에 넣은 데이터가 가장 먼저 튀어나오는 구조야. 프링글스 통에 감자칩을 차곡차곡 쌓아두면, 맨 밑에 있는 걸 꺼내려면 위에 있는 걸 다 빼야 하잖아? 딱 그거지
   1. 게임에서 어디에 써?
      1-1. UI 팝업창 관리 (뒤로 가기 기능): 게임 중에 상점 창을 켜고, 그 위에 설정 창을 켜고, 그 위에 인벤토리를 켰을 때, ESC를 누르면 가장 최근에 킨 인벤토리 창이 먼저 닫히지? 이럴 때 스택을 써
      1-2. 되돌리기(Undo) 기능: 그림판이나 에디터에서 실행 취소(Ctrl + Z)를 누를 때 가장 최근에 했던 행동부터 척척 취소되는 원리
   2. 핵심 키워드: 후입선출, 프링글스 통, 뒤로 가기/팝업창
- "Queue는 놀이공원 줄 서기처럼 먼저 들어온 데이터가 먼저 처리되는 선입선출 구조(스폰 대기열 등)에 쓰이고, Stack은 프링글스 통처럼 나중에 들어온 데이터가 먼저 나오는 후입선출 구조(UI 팝업창 관리, 뒤로 가기 등)에 주로 활용됩니다."


- 한 줄 정의(먼저 두 가지 개념을 다 언급하기): 힙(Heap)은 문맥에 따라 완전히 다른 두 가지 개념을 가짐. 첫째는 C# 객체와 동적 데이터가 관리되는 메모리 힙 영역이고, 둘째는 최댓값/최솟값을 빠르게 찾아내는 자료구조 힙(우선순위 큐).
- 메모리 관점 (Memory Heap):
   1-1. 개념: new 키워드로 생성된 클래스 객체나 대형 데이터가 동적으로 할당되는 거대한 물품 보관소 창고
   1-2. 특징: 스택과 달리 함수가 끝나도 자동으로 사라지지 않아서, 가비지 컬렉터(GC)라는 청소부가 주기적으로 돌며 정리해 줘야 해
   1-3. 불필요한 객체 생성을 줄이고 재사용하는 오브젝트 풀링이 필요한 이유가 바로 이 메모리 힙과 GC 부하를 줄이기 위함이지
   1-4. 오브젝트 풀링이 필요하다?: 
      1-a. 매번 새로 만들고(Instantiate) 부수고(Destroy) 반복 하면 힙 창고에 쓰레기가 쌓이고 GC 청소부가 계속 출동해서 게임이 끊기잖아?
      1-b. 그래서 "아예 게임 시작할 때 총알을 미리 딱 10개만 만들어두고(New), 파괴(Destroy)하지 말고 그냥 비활성화(SetActive(false))만 시켜두자!" 하는 거야
      1-c. 총알이나 각종 오브젝트가 필요하면 창고에서 꺼내서 쓰고, 볼일 다 보면 버리지 말고 다시 창고에 집어넣어서 재사용하는 거지 (창고: 오브젝트 풀(Object Pool) 변수, 코드로 따지면 Queue<GameObject> pool 같은 컬렉션 상자를 의미)
      1-d. 게임이 시작될 때 미리 만들어둔 총알, 오브젝트들을 힙 메모리에서 끌어와서, 네가 코드로 짠 오브젝트 풀 변수(Queue) 안에 차곡차곡 줄을 세워(Enqueue) 두는 거지, 
      그리고 총알이 필요할 때마다 그 큐에서 쏙 빼서 쓰고(Dequeue), 다 쓰면 다시 그 큐에 쏙 집어넣어서(Enqueue) 대기시키는 거야
      1-e. 이렇게 하면 Instantiate와 Destroy를 안 하니까 힙 메모리에 새로운 쓰레기가 안 쌓이고, GC 청소부가 출동할 일도 없어지니까 게임이 부드러워지는 거야!
   2. 즉, 매번 동적 할당과 해제(Instantiate/Destroy)를 반복하며 힙 메모리에 쓰레기를 만들고 GC 부하(렉)를 유발하는 대신, 게임 시작 시 미리 객체를 생성해 두고 비활성화/활성화(SetActive)를 통해 재사용함으로써 성능을 최적화하는 핵심 기법이 바로 오브젝트 풀링이다
-자료구조 관점 (Data Structure Heap):
   1-1. 개념: 들어온 순서와 상관없이 '우선순위가 가장 높은 데이터(최대/최솟값)'를 단번에 뽑아내기 위해 만든 완전 이진트리 구조
   1-2. 응급실이나 놀이공원 익스프레스 패스처럼, 들어온 순서 상관없이 "가장 우선순위가 높은 놈"이 먼저 튀어나오는 구조 (A* 길찾기 알고리즘, 우선순위 큐에 사용됨)
- AI 면접때 이 "힙(Heap)에 대해 설명해 주세요"라고 한다면? (역질문 불가 상황 대비 대처법).
   1. AI는 되물을 수 없으니, 처음부터 두 가지를 모두 짧게 언급한 뒤, 내가 주력으로 다루는 메모리 힙 쪽으로 무게중심을 두고 말하는 게 최고야
   2. "컴퓨터 과학에서 힙은 크게 두 가지 의미로 사용됩니다. 첫째는 클래스 객체나 동적 데이터가 할당되는 메모리 힙 영역으로, 가비지 컬렉터와 메모리 관리 관점에서 다루어집니다. 
   둘째는 우선순위가 가장 높은 데이터를 빠르게 찾아내기 위한 자료구조 힙으로, A 길찾기 알고리즘이나 우선순위 큐 등 게임 시스템 최적화와 효율적인 데이터 처리에 핵심적으로 활용됩니다."*


- 오브젝트 풀링(Object Pooling): 수영장(Pool)에 튜브들을 미리 바람 넣어두고 쌓아두는 거야. 사람이 올 때마다 공장에서 튜브를 새로 만들고(생성), 놀고 나면 버리는(파괴) 게 아니라, 수영장에서 꺼내 쓰고 다 쓰면 다시 수영장에 반납해서 재사용하는 거지.
   1. 게임에 어디에 써?
      1-1. 게임 중에 총알이나 몬스터가 튀어나올 때마다 Instantiate(생성)하고 죽을 때마다 Destroy(파괴)를 하면, 컴퓨터(CPU)가 메모리를 새로 할당하느라 멈칫거리고(렉 발생), 나중에 쓰레기 데이터가 쌓여서 가비지 컬렉터(GC)가 작동하면서 게임이 뚝뚝 끊기게 돼
      1-2. 이걸 막기 위해 미리 다 만들어두고, 껐다 켰다(Active/Deactive)만 반복하는 최적화 기법이 바로 오브젝트 풀링이야
   2. "오브젝트 풀링은 게임 중에 Instantiate와 Destroy를 반복하면 메모리 할당 부하와 가비지 컬렉터(GC)로 인한 렉이 발생하기 때문에, 
   사전에 미리 객체들을 생성해 둔 뒤 큐(Queue) 구조를 이용해 활성화/비활성화 방식으로 재사용하는 핵심 성능 최적화 기법이라고 이해하고 있습니다."
