- 어제 몬스터 공격 사거리 감지 로직을 수학적 계산 방식으로 전환함에 따라, 더 이상 필요 없어진 나무 프리팹의 SphereCollider 컴포넌트를 완전히 삭제.

- 몬스터 사거리 탐색 로직 개선 (포트폴리오 작성용 메모).
   1. 문제 상황 (Problem):
      1-1. LineRenderer로 표시되는 원형 사거리와 실제 공격 감지 범위가 일치하지 않아 원 밖에서도 나무를 공격하는 현상 발생
      1-2. 기존 물리 엔진(OverlapSphere)과 SphereCollider 감지 방식에 의존하다 보니, 물리 연산 부하가 생기고 감지 범위에 모호함이 생김
      1-3. 또, 몬스터의 공격 사거리에 나무가 들어와도 공격 타이머가 0초부터 다시 올라가는 로직 때문에 첫 타격 시 불필요한 공격 딜레이가 발생
   2. 고민 및 원인 분석 (Insight):
      2-1. 물리 콜라이더를 계속 유지하면 몬스터와 나무 간의 불필요한 의존성(결합도)이 높아지고, 감지 영역에 혼선이 생긴다고 판단
      2-2. 성능과 정확도를 위해 무거운 물리 연산 대신 순수 수학적 거리 계산(sqrMagnitude) 방식으로 전환하기로 결정!
      2-3. 단일 책임 원칙(SRP)도 준수하기 위해 탐색 로직을 GetNearestTree() 함수로 분리하고, isTargetInRange 플래그 변수를 도입하여 감지 즉시 첫 타격이 들어가도록 리펙토링
   3. 해결 및 결과 (Solution & Result):

   2. 인과관계와 고민: 물리 엔진(OverlapSphere)을 쓰면 왜 부하가 걸리고 의도치 않은 충돌이 생기는지 분석했고, 이를 순수 수학적 거리(sqrMagnitude)와 GetNearestTree() 함수로 분리하여 SRP를 지키기로 결정함

몬스터 스폰 및 데이터 주입(DI) 구조 리팩토링 (EnemySpawner 허브역할 증대)

- 목표: 몬스터가 씬에서 직접 데이터를 찾던 기존 방식을 개선하여, EnemySpawner가 중심이 되는 데이터 주입(Dependency Injection) 구조로 리팩토링하기, 런타임 성능 최적화 및 객체 간 의존성 낮추기.

- 기존 방식의 문제점.
   1. 불필요한 씬 검색 및 성능 부하: 몬스터가 생성되자마자 몬스터의 각 스크립트에서 Awake/Start() 에서 GameObject.Find나 컴포넌트 탐색을 수행. 만약 수십 마리가 동시 소환될 경우 프레임 드랍(렉) 유발 우려
   2. 강한 결합도(Tight Coupling): 난 느슨한 결합을 하고 있다 생각했고, 강한 결합을 써야 할땐 어쩔 수 없다. 생각해서 어쩔 수 없이 조금만 추가 한거라고 생각했지만,
   지금의 방식은 몬스터가 자신이 태어난 환경과 데이터들을 스스로 찾아야 하므로, 씬 구조나 매니저가 바뀔 때 몬스터 코드가 함께 망가지는 구조

- 해결 과정 & 적용한 구조.
   1. EnemySpawner 스크립트를 몬스터의 허브(Hub)로 지정: EnemySpawner가 몬스터를 Instantiate(생성)한 직후, 필요한 재료(EnemyData, WaypointGroup)를 직접 쥐여주는 데이터 주입 방식으로 변경
   2. 초기화 함수(Init) 도입:
      2-1. Enemy: Init(EnemyData)을 통해 속도 및 기본 데이터 초기화
      2-2. EnemyHealth: Init(EnemyData)을 통해 체력 설정 및 체력바 UI 생성
      2-3. EnemyMovement: Init(GameObject)을 통해 이동할 웨이포인트 경로 주입
   3. 유니티 이벤트 함수 최소화: 몬스터가 생성되자마자 스스로 데이터를 찾지 않고, 스포너의 명시적인 Init 호출 전까지 대기하도록 안전장치 마련

- [참고 개념] Init (초기화 메서드) 이란?
   1. 뜻: Initialize(초기화)의 줄임말
   2. 무슨 역할이야?: 
      2-1. 유니티는 오브젝트가 생성될 때 Awake나 Start라는 기본 함수가 자동으로 실행되잖아? 이때는 외부에서 데이터를 받아올 타이밍을 잡기 어렵거나 데이터가 꼬이는 문제가 생길 수 있어
      2-2. 그래서 Init()이라는 내가 직접 타이밍을 통제할 수 있는 이름의 메서드를 만들어 두고, 오브젝트를 생성한 주체(여기선 EnemySpawner)가 "자, 이 데이터를 가지고 지금부터 시작해" 하고 명시적으로 호출해 주는 방식이지
   3. 이걸 왜 쓸까?:
      3-1. 몬스터가 스스로 씬을 뒤져서 데이터를 찾을 필요 없이, 외부에서 필요한 재료(EnemyData, WaypointGroup)를 딱 받아와서 안전하게 세팅(currentSpeed, currentHealth 등)할 수 있기 때문
      3-2. 객체 간의 의존성을 끊어내고, 언제 어떤 데이터로 초기화되는지 흐름을 한눈에 파악할 수 있게 만드는 데이터 주입(DI)의 핵심 도구
- Enemy 스크립트의 Init 예시).
public void Init(EnemyData data)
{
    //① EnemySpawner가 넘겨준 에셋(Data)을 몬스터의 변수에 저장
    enemyData = data; 

    //② EnemyData에셋에 적힌 속도(Speed)를 가져와서 내 현재 속도(currentSpeed)로 세팅
    currentSpeed = enemyData.Speed; 

    //③ 게임 매니저가 있다면 "나 생성됐어!" 하고 등록
    if (GameManager.Instance != null) GameManager.Instance.AddEnemy(this);
}
   1. EnemySpawner가 몬스터를 낳음 (Instantiate)
      1-1. EnemySpawner가 Instantiate(currentData.enemyPrefab, ...)를 실행해
      1-2. 이 순간 맵에는 몬스터 프리팹이 복제되어서 툭 튀어나오지. 하지만 아직 이 몬스터는 어떤 데이터(체력, 속도)를 써야 할지 모르는 껍데기 상태야
   2. EnemySpawner가 데이터를 쥐여줌 (Init 호출)
      2-1. 스포너는 방금 낳은 몬스터에게서 Enemy 컴포넌트를 가져와 (bossObj.GetComponent<Enemy>())
      2-2. 그리고 내가 쓴 Init 메서드를 이렇게 호출해: enemy.Init(currentData.enemyData);
      2-3. 이때 괄호 안에 들어간 currentData.enemyData가 바로 Init의 파라미터인 EnemyData data로 전달되는 거야
   3. 쉽게 생각하면 EnemySpawner(외부)가 "내가 준비 다 해줄 테니까, 내 신호 받을 때까지 기다려... 자, 이제 시작해!" 하고 직접 켜주는 수동 스위치(리모컨) 같은 거야
      3-1. 유니티가 알아서 실행해 주는 기존 방식(Awake, Start) 대신, "내가 원할 때, 내가 원하는 데이터를 쥐여주면서 시작 타이밍을 통제하고 싶을 때" 만드는 함수가 바로 Init이야


- 오늘 평소보다 복잡했는데 어땟어?
   1. SRP(단일 책임 원칙)와 실무적 타협의 딜레마:
      1-1. 난 평소에는 "EnemySpawner가 몬스터 생성뿐만 아니라 데이터 주입, 경로 설정, 매니저 등록까지 너무 많은 걸 안고 있는 게 아닌가?" 하는 찝찝함, 지저분함을 느꼇어, 내 방식과 많이 달라서
      1-2. 하지만 유니티 엔진의 특성(컴포넌트 생명주기, 런타임 검색 부하)을 고려할 때, EnemySpawner가 중앙 집중식 '허브' 역할을 맡아서 완성품을 조립해 주는 구조가 훨씬 실용적이고 직관적이라는 것이 오히려 리펙토링에 있어 더욱 효율적이라 느꼈지
   2. 단순히 코드가 '작동하게' 는 것을 넘어서, "왜 이런 구조가 성능과 유지보수에 유리하지?", "내가 너무 SRP를 강박적으로 지키려고 했던걸까?" 를 깊이 고민하고 설계의 기초를 다진 의미 있는 시간이었어
   3. 완전히 이해하진 못했어. Init도 처음 써본 방식이야, 하나하나 다 알아가기엔 다음 할 일도 많고 밀린것도 많으니...일단 원리만을 빠르게 파악하고 넘어가려고 해

- 근데 결국 나같은 사람이 취업해야해. 거의 매일을 불안해서 쉬질 못해 개발하고 2주마다 꼬박꼬박 헌혈 다니고....물론 내 개인적인 생각이겠지만?,
  하지만 확실한건 난 성실하게 노력하고 있다고 당당히 말할 수 있어. 쉬었음청년 처럼 그냥 누워만 있으면서 꿈만 꾸고 있진 않았다면서. 지금까지 1년 넘게 적어온 내 개발일지들이 그 증거잖아.
.

- 현상: 플레이어가 나무를 배치하려고 마우스에 미리보기 상태로 띄워 둔 나무를 몬스터들이 적(타겟)으로 인식해서 냅다 공격해 버리는 버그 발생.
- 원인 분석:
   1. 미리보기 나무 프리팹은 실제 나무 프리팹을 그대로 복사(Instantiate)해서 만드는데, 이 프리팹 안에 몬스터가 탐색할 때 사용하는 체력 컴포넌트(TreeHealth)가 포함되어 있어(사실상 똑같은 나무 프리팹이니까)
   2. 몬스터는(EnemyAttack) 씬 전체를 뒤져 TreeHealth를 가진 오브젝트를 찾다 보니, 아직 땅에 심어지지 않은 '마우스 위의 미리보기 오브젝트'까지 타겟으로 잡아버린거지

- 빠른 해결 방법.
   1. PlacementManager 스크립트의 나무 미리보기 생성(SelectTree()) 함수 시점에, 미리보기 오브젝트에서 TreeHealth 컴포넌트를 강제로 파괴(Destroy)하도록 수정
   2. 진짜 나무가 슬롯에 심어질 때는 **원본 프리팹에서 새로 생성되므로** 게임 플레이에는 아무 지장이 없고, 미리보기 상태일 때만 몬스터의 인식 범위에서 완전히 제외됨
   3. 추가 리팩토링: 최근에 나무나, 몬스터의 대상 탐지 방식을 '콜라이더 검출'에서 '수학적 거리 계산' 방식으로 개편했잖아?, (8/3~8/5) 더 이상 쓰이지 않게 된 불필요한 콜라이더 관련 지역 변수(col)를 깔끔하게 정리

   1. 코드를 짤 때 아키텍처나 SRP(단일 책임 원칙), DI(의존성 주입) 같은 이론에 너무 얽매여 모든 책임을 한쪽(예: GameManager)으로 몰아넣으면 오히려 유지보수가 힘든 '괴물 스파게티 코드'가 될 수 있음을 경계해야 해
   2. 각 매니저(PlacementManager, GameManager) 스크립트가 자신의 고유 책임을 확실히 지키되, 필요한 순간에만 메서드를 통해 소통하는 현재의 구조가 실용적이고 알맞은 밸런스라는 것을 확인
   3. 나쁜 하드 코딩이란?:

      하지만 유니티 엔진에서는 이걸 '데이터 바인딩(인스펙터 할당)'이라고 부르며 적극적으로 권장하는 방식이라고 해 (하지만 결국 수동연결이잖아? 이건 내가 지양하는 방식이고. 난 이름이나, 태그 찾기로 주로 쓰잖아)

         3-a. GameObject applePrefab = Resources.Load<GameObject>("Prefabs/AppleTree"); 이 처럼 인스펙터 창에서 연결하는 게 아니라, 코드 안에 직접 프로젝트 폴더 내에서 오브젝트를 불러오거나 박아두는 경우,
         코드 내부에 "사과나무 프리팹은 무조건 이거야!" 하고 경로를 박아버림(파일의 위치나 이름이 변경되면 오류 100%)
      3-3. 지금은 인스펙터에 일일이 넣어주는 방식이지만, 나중에 프로젝트가 커지면 '주소값(Resources.Load)'도 아니고 '수동 연결'도 아닌, '의존성 주입 프레임워크(Zenject/Extenject 등)'를 공부하게 될 거야. 그러면 코드가 스스로 필요한 객체를 알아서 찾아오게 만들 수도 있거든

게임 시작 연출 및 일시정지 시스템 구현

- 메인 화면 씬 및 씬 전환 흐름 정리.
   1. 메인 화면과 게임 씬 간의 매니저 연동 구조를 다듬고 씬 전환 흐름 완성, 메인씬에 타이틀 제목 추가 및 버튼 크기 수정


- 게임씬에서 게임 시작 시 곧바로 몬스터, 조작이 움직이지 않도록 준비 시간(3초 카운트다운) 연출 추가.

- GameManager 스크립트에서 Time.timeScale을 활용한 게임 시작 전 일시정지(준비 시간) 구현.
   1. 게임 시작 직후 Time.timeScale = 0f로 설정하여 몬스터 스폰 및 나무 선택과 배치 등 전체 씬 정지
- WaitForSecondsRealtime을 활용한 3초 카운트다운 연출.
   1. 게임 시간이 멈춘(0) 상태에서도 정상적으로 작동하는 현실 시간 기준 타이머 구현
   2. 화면 중앙에 UI 텍스트로  3, 2, 1 및 "START!" 텍스트 동적 표시
- UI 컴포넌트 자동 검색(Find) 기능 적용.
   1. 인스펙터 수동 드래그 앤 드롭 방식을 지양하기에, Awake 시점에 GameObject.Find와 GetComponent를 이용해 ReadyText를 코드로 자동 탐색 및 제어
   2. 하드코딩이지만 한번 지정한 텍스트의 이름은 거의 변경하지 않기에 번거로운 수동 연결 방식을 피하기 위한 현재 나의 최선의 선택
- [버그 수정] 준비 시간 중 타워(나무) 배치 및 선택 제한.
   1. 시간 정지 상태(timeScale == 0f)에서 나무 선택 UI에 마우스 입력으로 인해 타워가 미리 심어지는 기획적 잔 버그를 발견
      1-1. 만약 이를 방치하면 몬스터는 움직이지 않는데 나무 배치는 가능해져서 밸런스에 문제가 발생할 가능성이 있어
   2. 그래서 PlacementManager 스크립트의 SelectTree와 TryPlantTree 함수 내부에 방어 코드를 추가하여 대기 시간 동안 타워 선택 및 배치를 원천 차단
      2-1. if (Time.timeScale == 0f) return;//게임 시작 전(대기 시간)에는 나무 선택 및 미리보기 생성을 차단

- 일시정지때의 WaitForSeconds와 WaitForSecondsRealtime의 차이? (Time.timeScale은 게임이 아예 멈추는거야 1이면 시간이 흐르고 0이면 멈추지)
   1. WaitForSeconds(3f) = 게임 속 시간 기준
      1-1. Time.timeScale = 1f일 때: 정상적으로 3초를 기다려
      1-2. Time.timeScale = 0f일 때 (게임 일시정지): 시간이 멈춰버렸기 때문에 영원히 3초가 지나가지 않아 (코루틴이 멈춰버림)
   2. WaitForSecondsRealtime(3f) = 현실 시간 기준
      2-1. Time.timeScale = 1f일 때: 정상적으로 3초를 기다려
      2-2. Time.timeScale = 0f일 때 (게임 일시정지): 게임 속 시간은 0이어도, 내 컴퓨터 시계는 가고 있으니까 진짜로 3초를 딱 기다린 뒤에 다음 코드로 넘어가
- 왜 카운트다운에 이걸 썼을까? 게임 시작 전에 3, 2, 1 카운트다운을 보여주려고 Time.timeScale = 0f(게임 일시정지)를 걸었잖아?
   1. 만약 여기에 그냥 WaitForSeconds(1f)를 썼다면, 게임 시간이(Time.timeScale) 0이라서 1초가 영원히 안 지나가고 카운트다운이 3에서 멈춰버렸을 거야
   2. 그래서 *게임은 멈춰서 몬스터나 적들은 얼려두되, 카운트다운 스톱워치만은 현실 시간으로 1초, 2초, 3초 째깍째깍 흘러가게 해라* 라는 뜻으로 WaitForSecondsRealtime(1f)를 쓴 거지!


- 오늘 어땠어?
   1. 처음 시작 전 일시정지 기능을 단순히 몬스터, 나무 관련 스크립트마다 상태를 체크하는 조건문을 넣기보다, Time.timeScale을 이용해 씬 전체의 시간을 제어하는 방식이 훨씬 코드를 깔끔하게 만들어준다는걸 알고 바로 실행했어
   2. 다만 시간이 멈춰도 Update() 나 입력 처리는 행동하기 때문에, 유저 인터랙션(클릭 등)이 일어나는 부분에는(SelectTree와 TryPlantTree함수에) 별도의 방어막(timeScale 체크)이 반드시 필요하다는 예외처리가 필수!
   3. 인스펙터에 일일이 오브젝트를 꽂는 (드래그&드롭) 방식보단 코드로 찾아오게 하는 편이 관리하기 훨씬 편하다는 것을 다시 한번 느껴, 물론 이름이 고정되어야 하는 '하드코딩' 이지만 UI간의 연결은 거의 다 자동찾기 Find로 하기에,
