나무(타워) 데이터 참조 구조의 개선 (인터페이스 도입), 카운트 식으로 n회 적중하면 나무가 파괴될 로직 준비

- 나무의 체력과 데미지 받는 로직의 TreeHealth 스크립트에서 특정 나무 스크립트(AttackTree)만 참조하도록 구현되어 있어, 새로운 나무(SlowTree 등)를 추가할 때마다 관련 코드를 계속 수정해야 하는 비효율적인 구조.
- 인스펙터에서 SO를 매번 수동으로 연결하는 방식은 최대한 줄일려고 하고, 휴먼 에러의 가능성이 가장 높은 원인이야.

- 해결 과정 (인터페이스 도입)
   1. 인터페이스 ITree 정의: 모든 나무 스크립트가 준수해야 할 '데이터 제공 규칙'을 만듦
   2. 구조 변경: TreeHealth 스크립트가 구체적인 나무 클래스를 알 필요 없도록, GetComponent<ITree>()를 통해 데이터를 요청하는 방식으로 변경
   3. 코드 개선: 나무별로 GetTreeData() 함수를 구현해서 데이터를 반환하게 함으로써, TreeHealth 스크립트가 어떤 나무든 상관없이 자동으로 데이터를 가져올 수 있게 함
      3-1. 그냥 그 대상에게 물건(SO)를 건내주기만 하지, 받는 대상이 누군지도, 알려고 하지 않아(결합도 감소)
      3-2. 기존의 방식(강한 결합): TreeHealth가 AttackTree라는 특정 클래스를 직접 지목해서 가져와야 했어. 이는 TreeHealth가 AttackTree의 존재를 100% 알아야만 작동한다는 뜻이며, 나무 종류가 하나라도 바뀌면 TreeHealth도 같이 수정해야 하는 `강한 의존성'을 가짐
      3-3. 인터페이스 도입 후(느슨한 결합): TreeHealth는 이제 "데이터를 제공할 수 있는 인터페이스(ITree)만 가지고 있으면 누구든 상관없어!"는 입장이야
         3-a. : MonoBehaviour, ITree 상속  , public TreeData GetTreeData(){ return treeData; }

- 1. 인터페이스 도입 전 (문제점: 강한 결합, Strong Coupling).
   1. TreeHealth 스크립트가 AttackTree라는 특정 클래스에 의존
   2. 새로운 나무(SlowTree)등 추가할 때마다 TreeHealth 스크립트를 수정해야 하거나, 비슷한 체력 관리 스크립트를 나무 종류별로 복사해서 만들어야 함 (내가 극도로 싫어하는 방식이지. 단순 반복)
   3. 나무 종류가 늘어날수록 관리할 스크립트가 기하급수적으로 늘어나는 '매우 비효율적인 구조'
- 2. 인터페이스 도입 후 (해결책: 느슨한 결합, Loose Coupling).
   1. TreeHealth 스크립트는 나무의 구체적인 타입(AttackTree, SlowTree 등)이 무엇인지 알 필요가 없어
   2. 오직 ITree라는 계약서(인터페이스)를 통해 "데이터를 제공할 수 있는 기능이 있는가?"만 확인(MonoBehaviour 옆에 .ITree를 적었나 확인)
   3. 확장성: FireTree, IceTree 등 만약에 추가할 새로운 나무를 수십 개 추가해도 TreeHealth의 코드는 단 한 줄도 수정할 필요가 없지. 인터페이스를 구현(상속)하기만 하면 즉시 연동
- 인터페이스는 단순히 코드를 짧게 만드는 도구가 아니라, "나중에 새로운 기능을 추가할 때 기존 코드를 건드리지 않아도 되는 유연한 시스템을 만드는 설계 도구"라는 것을 이해하기 시작.
   1. 구체적인 클래스에 의존하지 말고, 추상적인 규칙(인터페이스)에 의존하라"는 설계 원칙을 실무에 적용해 본 소중한 경험

- 오늘의 평?
   1. 의존성 줄이기: 클래스 간의 강한 결합을 끊어내니, 새로운 기능을 추가해도 기존 코드를 건드릴 필요가 없는 '확장성 있는 구조'가 무엇인지 다시금 체감
   2. 만약의 면접 대비 포인트: "왜 인터페이스를 썼는가?"에 대해 단순히 코드가 짧아져서가 아니라, '의존성 역전(Dependency Inversion)'과 '확장성' 측면에서 설계의 중요성을 고민해봤다는 증거
   3. 구현하는 것에만 급급하지 않고, "이게 왜 더 좋은 코드인가? 다른 편한 방식은 없을까?"를 스스로 질문하고 의심해서 더 나은 해결책을 찾아가는 과정이 개발자로서 한 단계 성장한 느낌을 줌
   4. 처음으로 인터페이스에 대해 사용해봐서 많이 모르겠어. 당장은 쉽게 이해하려고만 했어. 다음에 자주 써서 더욱 숙달되게 해보자
   4. 이제부터 큰 일이 아니면 토, 일요일에는 손을 놓을려고 해. 의지박약? "너, 이러면 취업 못해" 생각은 많이 들꺼야. 하지만....솔직히 말해서 1년동안 매일 노력 했지만 결과는? ....응. 의지 박약일 수도 있어. 그래도 좀 쉬고 싶어

GameManager, PlacementManager 스크립트의 싱글톤 방식의 차이, 싱글톤 패턴과 오브젝트 생명주기 설계 (심화)

- DontDestroyOnLoad를 쓰냐, 안쓰냐의 차이야. 지금은 GameManager 스크립트에서만 DontDestroyOnLoad를 쓰고있어.
- 현재는 데이터(currentGold)는 PlacementManager 스크립트에서 관리하며, DontDestroyOnLoad를 사용하지 않음.

- GameManager (데이터 저장소).
   1. 향후 설계: DontDestroyOnLoad 적용 및 모든 씬에 배치
   2. 이유: 골드, 레벨, 업그레이드 수치 등 '게임 전체의 상태(State)'를 관리. 씬이 전환되어도 데이터가 소실되지 않고 유지되어야 하므로, 씬 이동 시에도 살아남아야 하기에
   3. 구현: Awake에 싱글톤 중복 방지 로직(if (Instance != null) Destroy)을 추가하여, 어떤 씬에서든 단 하나의 GameManager만 존재하도록 설계
- PlacementManager (현장 로직 관리자).
   1. 설계: DontDestroyOnLoad 미적용 (씬 전환 시 삭제)
   2. 이유: 나무 배치 로직, 타워 슬롯 참조 등 '해당 씬의 환경'에 종속된 객체들을 관리. 씬이 바뀌면 이전 씬의 타워 슬롯 참조는 더 이상 유효하지 않거나 에러를 유발하므로, 새로운 씬에 맞춰 새로 초기화되는 것이 안전해
   3. 구현: 씬 전환 시(사실상 게임 종료) 자연스럽게 파괴되도록 하여, 새로운 씬의 오브젝트들과 다시 연결되게 함
- (핵심).
   1. 데이터는 '죽지않게' (GameManager): 데이터는 씬을 건너뛰어도 생존해야 하므로 항상 모든 씬에 존재해야 한다
   2. 로직은 '현장에서만' (PlacementManager): 로직과 참조는 그 씬에 국한되어야 하므로, 씬이 바뀌면 깨끗하게 정리(Destroy)되는 것이 버그를 예방하는 가장 좋은 방법

- 현 상황 판단: 두 스크립트의 방식은 현재는 유지하도록 결정.
   1. 결정 이유: 현재 프로젝트는 게임 씬 내에서 플레이를 완료하는 구조
   2. 씬 전환 정책: 메인 화면으로의 이동은 곧 '게임 종료 및 초기화'를 의미 하니까, 따라서 씬이 전환될 때 데이터가 초기화되는 것은 버그가 아니라 의도된 결과
- 향후 확장성 고려 (GameManager와의 역할 분리).
   1. 향후 계획: 만약 추후에 '상점 시스템', '누적 업그레이드' 등 메인 화면과 그 외의 데이터 연동이 필요한 기능이 추가될 경우, 데이터의 주체를 GameManager로 이전하고 DontDestroyOnLoad를 적용할 계획
   2. 핵심 철학: 현재는 프로젝트의 복잡도를 낮추기 위해 '필요한 최소한의 기능'에 집중. 기능이 추가될 때마다 구조를 단계적으로 개선해 나갈 예정
- 결론으로:
   1. 현재는 씬 전환 시 데이터가 초기화되는 구조지만, 추후 게임씬 외에서의 '업그레이드 시스템'이 도입될 경우, 데이터의 영속성을 위해 GameManager를 통한 골드 통합 관리를 최우선으로 구현할 계획

- 예시: 골드의 성격 변화.
   1. 현재: "한 판짜리 소모성 자원" (게임 씬에서만 필요)
   2. 업그레이드 추가 후: "지속 가능한 자산" (메인 화면과 게임 씬을 넘나들어야 함)
- 이때의 데이터 구조 (GameManager의 역할), GameManager에 currentGold를 두면 이런 마법이 가능해져.
   1. 게임 씬 종료 시: PlacementManager에 있던 남은 골드를 GameManager.Instance.currentGold에 저장해
   2. 메인 화면 이동: GameManager는 DontDestroyOnLoad 덕분에 죽지 않고 메인 화면으로 골드를 들고 이동해
      2-1. 게임 씬에만 GameManager을 두면 씬을 이동할 때 데이터가 삭제되거나, 메인 화면에서 데이터를 읽을 수 없으므로, 모든 씬에 배치하고 싱글톤 로직을 제어
   3. 메인 화면 업그레이드: 상점에서 공격력 업그레이드를 눌러? 그럼 GameManager.Instance.currentGold -= 100;을 실행해. 골드가 줄어들겠지?
   4. 다시 게임 씬 입장: GameManager는 줄어든 골드(혹은 새로 번 골드)를 그대로 유지한 채 다시 게임 씬으로 가

   3-1. 데이터의 외부화: 지금처럼 ScriptableObject로 데이터(수치)를 완벽하게 분리하고, "기획자가 엑셀로 데이터를 관리한다고 가정했을 때, 이를 어떻게 유니티에 불러올까?"를 고민해 봐
   3-2. 생명주기 관리 (Object Pooling): Instantiate와 Destroy를 계속 쓰면 메모리가 파편화돼. 총알을 100개 미리 만들어두고 껐다 켰다 하는 '오브젝트 풀링(Object Pooling)'을 적용해 봐. 이건 게임 개발자라면 반드시 물어보는 필수 질문이야!
   3-3. 예외 처리와 로깅: Try-Catch를 쓰거나, 데이터가 없을 때 Debug.LogError로 멈추는(Fail-fast) 로직. "예상치 못한 상황이 벌어졌을 때 프로그램이 죽지 않고 어떻게 로그를 남길 것인가"에 대한 고민
4. '왜' 결합도를 낮추려고 했는지 적어두기: "결합도를 낮추니 깔끔해졌다"는 결과도 좋지만, "결합도가 높으면 A 코드를 수정할 때 B 코드까지 건드려야 해서 수정이 번거롭고 복잡했는데 옵저버 패턴 등 이벤트 신호를 전하고 받는 식으로 수정하니,
   이젠 걱정이 사라졌다" 같은 감정을 한 줄 덧붙이면, 현업 개발자의 고충을 이미 경험하고 해결했다는 게 더 잘 느껴질거야!
